# Skills DESIGN

> `skills/` 现在是一个轻量目录，不是 vendor 仓库，也不是未来信誉系统的提前实现。

## 目标

这份设计只解决 3 件事：

1. 让人快速看懂 `skills/` 目录在收什么。
2. 让我们把“值得现在关注的实用方向”和“值得观察的有趣项目”分开。
3. 给后续收录条目一个最小模板，避免 README 越写越散。

换句话说，`skills/` 目前承担的是发现和整理职责，不承担正式评级、导入、打包和信任结算职责。

## 不做什么

当前版本明确不做：

- 不建立 L0-L4 之类的复杂分类体系
- 不做 `certified / curated / experimental / deprecated` 成熟度治理
- 不做证据等级、打分表、审计流程
- 不把第三方 Skill 仓库 vendoring 到本仓库
- 不把 `skills/` 写成未来 reputation / marketplace / task matching 系统的白皮书

如果某个想法还没有对应到当前目录的实际使用方式，就先不要写进这里。

## 轻量收录原则

无论是实用条目还是有趣条目，至少要能回答下面几个问题：

- 它到底在帮谁做什么？
- 它更像 `实用主线`，还是 `有趣实验区`？
- 它展示的 workflow 形状是什么？
- 为什么 RedAnet 现在值得关心它？

优先记录 workflow，而不是热词。

优先记录边界清楚、说明简短的条目，而不是堆很长的世界观。

默认增量维护：一批只加少量条目，避免目录迅速失控。

对 `有趣实验区` 再加一条硬门槛：

- 默认要求 `stars >= 100`，或者能看到明确的公开讨论信号
- 如果一个外部项目 `stars < 100` 且几乎没有公开讨论，就先不收录

这里的“公开讨论信号”不做复杂打分，但至少要能举出具体证据，例如：

- 有持续的 issue 或 discussion
- fork 明显不只是作者自用
- 被公开列表、文章或其他仓库反复引用

## 双轨模型：实用 / 有趣

### 实用主线

实用主线面向 RedAnet 近期真实任务形态，优先覆盖：

- 工程协作
- 研究与证据整理
- 工作流与集成
- 文档与数据处理

判断标准很简单：如果一个方向很可能在未来几轮 issue 里直接转化为交付、验收或协作能力，它就该先放这里。

### 有趣实验区

有趣实验区允许收录整活、人格蒸馏、关系理解、反蒸馏这类项目，但必须满足两点：

1. 能看出明确的 workflow 形状或表达启发
2. 条目要带来源和免责声明，不暗示“已经采用”

这里的重点不是证明它可用，而是记录它为什么值得观察。

## 最小条目模板

后续新增条目时，优先用这个最小模板，而不是重新发明一套重型元数据：

```yaml
name: example-skill
source: https://github.com/example/example-skill
track: interesting
hook: 一句话说明它为什么值得看
workflow_shape: 输入如何被整理成输出
why_redanet_cares: 它和当前目录或任务形态的关系
status: watching
```

字段说明：

- `name`：条目标识
- `source`：外部来源链接
- `track`：`practical` 或 `interesting`
- `hook`：一句话看点
- `workflow_shape`：最值得借鉴的流程结构
- `why_redanet_cares`：为什么对当前仓库有意义
- `status`：当前观察状态，默认用 `watching` 或 `want-to-try`

## 后续何时再升级

只有在下面这些情况同时出现时，才值得把这份设计再升级：

- 目录条目明显变多，README 已经装不下
- 某些条目开始需要本地试装、验证或封装
- 我们真的准备把其中一部分做成项目内 Skill 包

在那之前，优先保持目录轻、入口清楚、增量可维护。
