# Skills DESIGN

> `skills/` 的当前方向是：收录第三方公开 `SKILL.md`，补最小元数据，再交给 manager 做挑选和安装。

## 目标

这份设计现在只解决 4 件事：

1. 定义第三方 Skill 怎么进入仓库
2. 定义最小元数据需要覆盖什么
3. 定义 manager 至少要能做什么
4. 保持整体体验偏“懒人/傻瓜式”，而不是要求用户手工拼装

它不再是“有趣 Skill 观察名单”的设计说明，也不是未来信誉系统的预演。

## 不做什么

当前版本明确不做：

- 不先做复杂评级、信誉系统或 marketplace
- 不先做大而全 taxonomy
- 不要求第一版支持所有上游来源和所有 Skill 变体
- 不要求第一版解决自动同步和全量更新策略
- 不把 manager 设计成一个过重的平台

先把最小闭环跑通，再谈更大的治理层。

## 最小系统模型

当前要形成的是一个三段式结构：

1. `第三方 Skill 来源`
2. `仓库内 Skill 库`
3. `Skills manager`

关系很简单：

- 外部公开仓库提供 `SKILL.md`
- 我们把它抓进仓库，补最小元数据
- manager 基于这些内容做浏览、筛选和安装

## 最小入库单元

每个已入库 Skill 至少应有两部分：

- `SKILL.md`
- `metadata`

`metadata` 不要求一开始就很复杂，但至少要覆盖这些信息：

- 唯一标识
- 来源仓库
- 来源路径或来源定位信息
- 一句话摘要
- 基本标签
- manager 用于展示和安装的必要信息

只要 manager 还要靠猜，元数据就还不够。

## Manager 最小能力

第一版 manager 至少支持：

- `list`：列出库里有哪些 Skill
- `search`：按关键词或标签筛选
- `show`：查看某个 Skill 的元数据
- `install`：把选中的 Skill 装到目标位置

如果没有这 4 个动作，就还称不上“傻瓜式挑选安装”。

## 设计原则

- `SKILL.md` 是核心收录对象，不是只保存外链
- 元数据先小后大，先够 manager 用
- 目录结构服务安装流程，不服务抽象分类
- 先支持最小可用路径，再考虑批量同步和质量治理
- 任何新复杂度都要回答：它是否直接改善“收、看、选、装”

## 后续升级条件

只有在下面这些情况出现时，才值得把设计升级得更重：

- 库里的 Skill 数量已经让最小元数据不够用
- manager 的筛选和安装需求开始逼出更丰富的字段
- 上游同步、版本跟踪和冲突处理变成真实问题

在那之前，优先保持目标直接：

- 抓进来
- 补元数据
- 能安装
